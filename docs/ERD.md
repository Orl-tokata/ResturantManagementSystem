# Step 3 — Data Model

Follows [ARCHITECTURE.md](ARCHITECTURE.md) and [SCREENS.md](SCREENS.md).

15 tables exist. This step adds 12 and changes 6. Everything below is written
against the real DDL in `V2__init.sql`, not against a sketch.

**House rules already in force, kept:** money is `NUMERIC(12,2)`; riel is
`NUMERIC(14,0)` because the riel has no minor unit; portable DDL only, so the
same migration runs on H2 and PostgreSQL; `act_yn` + `reg_id/reg_dtm/mod_id/
mod_dtm` on every business table.

---

## 1. Four things the current schema gets wrong

Found by reading the DDL, not by inspection of the feature list. Each one
silently produces wrong numbers today.

### 1.1 `biz_key` cannot become a tenant key

```sql
CONSTRAINT uk_users_biz_key UNIQUE (biz_key)
```

It is **unique per user**. A company with three staff would violate it on the
second insert. So it is not a tenant identifier that nothing uses — it is a
per-user random string that structurally *cannot* be one.

> Do not repurpose it. Add `company` and `branch` as real tables, and leave
> `biz_key` alone or drop it. Retrofitting it would mean dropping a unique
> constraint on a populated column and hoping.

### 1.2 `order_item` does not record cost

It stores `unit_price` but not unit cost. `product.cost` is a mutable column,
so every profit report recomputes last month's margin using today's cost.

`product_name` is already denormalised onto the line, with a comment explaining
why — a receipt must survive a rename. **Cost deserves the same reasoning and
did not get it.** This is the same class of bug as the exchange rate in
ARCHITECTURE §10, and it is the one that makes profit reports untrustworthy.

### 1.3 `supplier.balance` is a running total with no ledger

```sql
balance NUMERIC(12,2) NOT NULL DEFAULT 0
```

A mutable number nothing can reconstruct. Identical anti-pattern to
`product.stock_qty`. When it disagrees with reality there is no way to find out
where it went wrong.

### 1.4 `stock_movement` is narrower than it looks

```sql
movement_type CHECK (movement_type IN ('IN', 'OUT', 'DAMAGED'))
qty           CHECK (qty > 0)
stock_item_id NOT NULL  -- ingredients only
```

Three types, no reference to the causing document, no product FK, and it cannot
express a sale because sales are of products. Direction lives in the type
rather than the sign, which is a legitimate choice — **keep it**, and widen the
type list instead of resigning the quantity.

## 2. Changes to existing tables

| Table | Change | Why |
|---|---|---|
| `orders` | drop `payment_method`, `amount_tendered`, `change_amount` → `sale_payment` | split payment (SCREENS §2.1) |
| `orders` | + `customer_id`, `shift_id`, `fx_rate_khr`, `idempotency_key` | loyalty, shift reports, dated rate, duplicate protection |
| `orders` | status + `REFUNDED`, `PARTIALLY_REFUNDED` | returns |
| `order_item` | + `unit_cost`, `discount_amount`, `promotion_id` | §1.2, and per-line promotions |
| `stock_movement` | + `product_id` (nullable), `ref_type`, `ref_id`, `branch_id` | a movement must name its cause |
| `stock_movement` | types → `PURCHASE SALE ADJUST TRANSFER WASTE RETURN` | `IN/OUT/DAMAGED` cannot express a sale |
| `product` | + `has_variants`, `track_stock`, `barcode` | variants; and a dish that is cooked to order tracks no stock |
| `product` | `stock_qty` → derived, not written directly | ARCHITECTURE §6 |
| `users_infm` | + `branch_id`; CHECK gains `MANAGER` | scoping, and the role Step 2 assumes |
| `staff` | CHECK gains `MANAGER` | same |
| `supplier` | `balance` → derived from `supplier_ledger` | §1.3 |

**`orders` keeps its name.** Renaming it to `sale` would touch 76 endpoints,
every test and the migration history, to buy a word. The brief's "sale" and
this system's "order" are the same thing.

## 3. New tables

### 3.1 Organisation

```sql
CREATE TABLE company (
    id        BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name      VARCHAR(150) NOT NULL,
    name_en   VARCHAR(150),
    tax_id    VARCHAR(50),
    act_yn    VARCHAR(1)   NOT NULL DEFAULT 'Y',
    ...audit
);

CREATE TABLE branch (
    id          BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    company_id  BIGINT       NOT NULL REFERENCES company (id),
    code        VARCHAR(20)  NOT NULL,
    name        VARCHAR(150) NOT NULL,
    name_en     VARCHAR(150),
    address     VARCHAR(500),
    phone       VARCHAR(30),
    act_yn      VARCHAR(1)   NOT NULL DEFAULT 'Y',
    ...audit,
    CONSTRAINT uk_branch_code UNIQUE (company_id, code)
);
```

`branch_id` then goes on: `orders`, `product`, `stock_item`, `stock_movement`,
`purchase`, `dining_table`, `users_infm`, `cash_shift`, `customer`.

> **Do this first, and in one migration.** With 172 orders it is an afternoon.
> The seed row is company 1 / branch 1, every existing row backfills to it, and
> the column is `NOT NULL` from the start — a nullable tenant key becomes a
> permanent source of rows belonging to nobody.

**Not `company_id` on every table.** Branch implies company; carrying both is
denormalisation that will drift. Join through `branch`.

### 3.2 Shift and cash

```sql
CREATE TABLE cash_shift (
    id             BIGINT         GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    branch_id      BIGINT         NOT NULL REFERENCES branch (id),
    user_ref       BIGINT         NOT NULL REFERENCES users_infm (id),
    opened_at      TIMESTAMP      NOT NULL,
    closed_at      TIMESTAMP,
    opening_float  NUMERIC(12, 2) NOT NULL,
    declared_cash  NUMERIC(12, 2),
    expected_cash  NUMERIC(12, 2),
    variance       NUMERIC(12, 2),
    note           VARCHAR(500),
    status         VARCHAR(20)    NOT NULL DEFAULT 'OPEN',
    ...audit,
    CONSTRAINT ck_shift_status CHECK (status IN ('OPEN', 'CLOSED'))
);

CREATE UNIQUE INDEX ux_shift_one_open
    ON cash_shift (branch_id, user_ref) WHERE status = 'OPEN';
```

**That partial index is the whole design.** One open shift per user per branch,
enforced by the database rather than by a service method that can be raced. Two
tills, one login, two floats — otherwise perfectly possible.

> **Portability cost, stated plainly:** partial indexes are PostgreSQL-only.
> H2 in PostgreSQL mode will reject that `WHERE`. Either the `dev` profile
> moves to PostgreSQL (it is already a Windows service here and CI already runs
> a Testcontainers suite), or this constraint lives in application code and is
> weaker. **Recommend moving `dev` to PostgreSQL** — the H2 fallback has
> already cost this project two migration bugs that PostgreSQL would have
> caught, and the environments diverging is itself the risk.

```sql
CREATE TABLE cash_movement (
    id         BIGINT         GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    shift_id   BIGINT         NOT NULL REFERENCES cash_shift (id),
    type       VARCHAR(20)    NOT NULL,
    amount     NUMERIC(12, 2) NOT NULL,
    reason     VARCHAR(500),
    ref_type   VARCHAR(30),
    ref_id     BIGINT,
    created_by VARCHAR(50)    NOT NULL,
    created_at TIMESTAMP      NOT NULL,
    CONSTRAINT ck_cash_mv_type
        CHECK (type IN ('SALE','REFUND','PAY_IN','PAY_OUT','FLOAT','DROP'))
);
```

`expected_cash` is `opening_float` + sum of movements. Never stored mid-shift,
only at close — a stored running total is §1.3 again.

### 3.3 Payments

```sql
CREATE TABLE sale_payment (
    id              BIGINT         GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id        BIGINT         NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
    method          VARCHAR(20)    NOT NULL,
    amount          NUMERIC(12, 2) NOT NULL,
    amount_khr      NUMERIC(14, 0),
    tendered        NUMERIC(12, 2),
    change_amount   NUMERIC(12, 2),
    reference       VARCHAR(100),
    khqr_md5        VARCHAR(32),
    status          VARCHAR(20)    NOT NULL DEFAULT 'CAPTURED',
    created_at      TIMESTAMP      NOT NULL,
    CONSTRAINT ck_payment_method CHECK (method IN ('CASH','CARD','KHQR','TRANSFER')),
    CONSTRAINT ck_payment_status CHECK (status IN ('PENDING','CAPTURED','FAILED','REFUNDED'))
);
```

An order is paid when its captured payments cover its total. Cash change comes
off the cash line only — a customer does not get change from a QR.

> **`CARD` and `TRANSFER` are still trust-based labels.** No terminal is
> integrated; a cashier asserting "card" is the entire verification. That was
> true before this change and stays true. KHQR is the one method the system can
> actually confirm, and it should stay visibly different in the UI for that
> reason.

### 3.4 Customers and loyalty

```sql
CREATE TABLE customer (
    id          BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    branch_id   BIGINT       NOT NULL REFERENCES branch (id),
    code        VARCHAR(20)  NOT NULL,
    name        VARCHAR(150) NOT NULL,
    phone       VARCHAR(30),
    email       VARCHAR(120),
    birth_date  DATE,
    note        VARCHAR(500),
    act_yn      VARCHAR(1)   NOT NULL DEFAULT 'Y',
    ...audit,
    CONSTRAINT uk_customer_code UNIQUE (branch_id, code)
);

CREATE INDEX ix_customer_phone ON customer (phone);
```

**Phone is indexed but not unique.** It is the lookup key at the till, and it
is also shared between a husband and wife, reassigned by the carrier, and
mistyped. A unique constraint on it turns a routine data-entry slip into a
blocked sale at a queue.

`points_balance` is deliberately **absent** — it is the sum of the ledger:

```sql
CREATE TABLE loyalty_transaction (
    id          BIGINT         GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT         NOT NULL REFERENCES customer (id),
    order_id    BIGINT         REFERENCES orders (id),
    type        VARCHAR(20)    NOT NULL,
    points      NUMERIC(12, 2) NOT NULL,
    note        VARCHAR(255),
    created_at  TIMESTAMP      NOT NULL,
    CONSTRAINT ck_loyalty_type
        CHECK (type IN ('EARN','REDEEM','ADJUST','EXPIRE','REVERSE'))
);
```

`points` is signed here — unlike stock, where direction lives in the type.
Inconsistent, and worth admitting: stock's convention is already established in
a populated table, and changing it is churn. New tables get signed amounts.

### 3.5 Promotions

```sql
CREATE TABLE promotion (
    id            BIGINT         GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    branch_id     BIGINT         NOT NULL REFERENCES branch (id),
    name          VARCHAR(150)   NOT NULL,
    type          VARCHAR(20)    NOT NULL,
    value         NUMERIC(12, 2) NOT NULL,
    scope         VARCHAR(20)    NOT NULL,
    scope_id      BIGINT,
    min_amount    NUMERIC(12, 2),
    starts_at     TIMESTAMP      NOT NULL,
    ends_at       TIMESTAMP      NOT NULL,
    time_from     TIME,
    time_to       TIME,
    act_yn        VARCHAR(1)     NOT NULL DEFAULT 'Y',
    ...audit,
    CONSTRAINT ck_promo_type  CHECK (type IN ('PERCENT','AMOUNT','BUY_X_GET_Y')),
    CONSTRAINT ck_promo_scope CHECK (scope IN ('ITEM','CATEGORY','ORDER')),
    CONSTRAINT ck_promo_dates CHECK (ends_at > starts_at)
);
```

`BUY_X_GET_Y` is in the CHECK but not in Phase 1 (SCREENS §3.5). The
constraint allows it so the enum does not need a second migration later.

### 3.6 Variants and modifiers

```sql
CREATE TABLE product_variant (
    id         BIGINT         GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id BIGINT         NOT NULL REFERENCES product (id) ON DELETE CASCADE,
    sku        VARCHAR(50),
    barcode    VARCHAR(50),
    name       VARCHAR(100)   NOT NULL,
    name_en    VARCHAR(100),
    price      NUMERIC(12, 2) NOT NULL,
    cost       NUMERIC(12, 2) NOT NULL DEFAULT 0,
    sort_order INTEGER        NOT NULL DEFAULT 0,
    act_yn     VARCHAR(1)     NOT NULL DEFAULT 'Y',
    ...audit
);

CREATE TABLE modifier_group (
    id         BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name       VARCHAR(100) NOT NULL,
    name_en    VARCHAR(100),
    min_select INTEGER     NOT NULL DEFAULT 0,
    max_select INTEGER     NOT NULL DEFAULT 1,
    ...audit
);

CREATE TABLE modifier (
    id             BIGINT         GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    group_id       BIGINT         NOT NULL REFERENCES modifier_group (id),
    name           VARCHAR(100)   NOT NULL,
    name_en        VARCHAR(100),
    price_delta    NUMERIC(12, 2) NOT NULL DEFAULT 0,
    ...audit
);

CREATE TABLE product_modifier_group (
    product_id BIGINT NOT NULL REFERENCES product (id) ON DELETE CASCADE,
    group_id   BIGINT NOT NULL REFERENCES modifier_group (id),
    PRIMARY KEY (product_id, group_id)
);

CREATE TABLE order_item_modifier (
    id            BIGINT         GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_item_id BIGINT         NOT NULL REFERENCES order_item (id) ON DELETE CASCADE,
    modifier_id   BIGINT         REFERENCES modifier (id),
    modifier_name VARCHAR(100)   NOT NULL,
    price_delta   NUMERIC(12, 2) NOT NULL DEFAULT 0
);
```

`modifier_name` denormalised for the same reason `product_name` already is: the
receipt must stay true after a rename. `modifier_id` nullable so deleting a
modifier does not destroy history.

### 3.7 Returns

```sql
CREATE TABLE sale_return (
    id             BIGINT         GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id       BIGINT         NOT NULL REFERENCES orders (id),
    branch_id      BIGINT         NOT NULL REFERENCES branch (id),
    shift_id       BIGINT         REFERENCES cash_shift (id),
    return_no      VARCHAR(20)    NOT NULL UNIQUE,
    reason         VARCHAR(500)   NOT NULL,
    total          NUMERIC(12, 2) NOT NULL,
    refund_method  VARCHAR(20)    NOT NULL,
    approved_by    BIGINT         REFERENCES users_infm (id),
    ...audit
);

CREATE TABLE sale_return_item (
    id             BIGINT         GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    return_id      BIGINT         NOT NULL REFERENCES sale_return (id) ON DELETE CASCADE,
    order_item_id  BIGINT         NOT NULL REFERENCES order_item (id),
    qty            NUMERIC(12, 2) NOT NULL CHECK (qty > 0),
    line_total     NUMERIC(12, 2) NOT NULL
);
```

A separate document rather than negative rows on the original order. The
original sale is a printed, signed historical record and must not mutate.

**No database constraint can stop over-returning** — returning 3 of a line of 2
across two documents needs a sum across returns. That is a service-layer check,
and naming it here means it will not be forgotten.

### 3.8 Audit and idempotency

```sql
CREATE TABLE audit_log (
    id          BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    branch_id   BIGINT,
    user_ref    BIGINT       REFERENCES users_infm (id),
    user_id     VARCHAR(50)  NOT NULL,
    action      VARCHAR(30)  NOT NULL,
    entity      VARCHAR(50)  NOT NULL,
    entity_id   BIGINT,
    before_json VARCHAR(4000),
    after_json  VARCHAR(4000),
    ip          VARCHAR(45),
    created_at  TIMESTAMP    NOT NULL
);

CREATE INDEX ix_audit_entity ON audit_log (entity, entity_id);
CREATE INDEX ix_audit_created ON audit_log (created_at);
```

`user_id` is copied as text as well as referenced, so the log still names
someone after the account is deleted. No `act_yn`, no update path, no delete
endpoint — an audit log that can be edited is not one.

```sql
CREATE TABLE idempotency_key (
    id           BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    key_value    VARCHAR(80)  NOT NULL UNIQUE,
    endpoint     VARCHAR(120) NOT NULL,
    response_ref BIGINT,
    created_at   TIMESTAMP    NOT NULL
);
```

The unique constraint *is* the mechanism: the second request loses the insert
and returns the first response instead of creating a second bill.

### 3.9 Dated exchange rate

```sql
CREATE TABLE fx_rate (
    id         BIGINT         GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    currency   VARCHAR(3)     NOT NULL,
    rate       NUMERIC(14, 4) NOT NULL,
    valid_from DATE           NOT NULL,
    created_by VARCHAR(50),
    created_at TIMESTAMP      NOT NULL,
    CONSTRAINT uk_fx UNIQUE (currency, valid_from)
);
```

And `orders.fx_rate_khr` stamped at settlement. The table is the history; the
stamp is what a reprint reads. Both, because a rate corrected retroactively
must not rewrite a receipt that a customer is holding.

## 5. Migration order

Flyway is at V5. These are V6 onwards, and the order is not arbitrary —
each depends on the one before.

| | Migration | Depends on |
|---|---|---|
| V6 | `company`, `branch`, backfill `branch_id` everywhere | — |
| V7 | `MANAGER` in role CHECKs | — |
| V8 | `cash_shift`, `cash_movement` | V6 |
| V9 | `sale_payment` + migrate `orders.payment_method` | V6, V8 |
| V10 | widen `stock_movement`; `order_item.unit_cost` | V6 |
| V11 | `audit_log`, `idempotency_key`, `fx_rate` | V6 |
| V12 | `customer`, `loyalty_transaction` | V6 |
| V13 | `product_variant`, modifiers | V6 |
| V14 | `promotion` | V6, V13 |
| V15 | `sale_return`, `sale_return_item` | V9, V10, V12 |
| V16 | `supplier_ledger`; `supplier.balance` derived | V6 |

**V9 and V10 carry data, not just structure.** V9 must read each paid order's
`payment_method` and write a `sale_payment` row before dropping the column;
V10 must backfill `unit_cost` from `product.cost`, which will be *wrong* for
historical lines — there is no way to recover a cost that was never recorded.

> Say so in the migration comment and in the reports UI: margin before the
> V10 cutover is an estimate. Silently plausible wrong numbers are worse than
> a labelled gap, and this project has already been bitten once by a
> substitution that was silent.

**Back up before V6 and V9.** The database is a Windows service on this machine
with 172 real orders in it.

## 6. Sizing

At 200 orders a day, ~6 lines each: `orders` 73k/year, `order_item` 440k/year,
`stock_movement` ~500k/year, `audit_log` the largest by far.

Nothing here needs partitioning at this scale. It needs indexes on
`(branch_id, reg_dtm)` for every reporting query, and an archival policy for
`audit_log` before year three.
